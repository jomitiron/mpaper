Building the new MotoPapers

How we ship the Direction C redesign on top of the existing MotorPapers API: what we build, what the backend has to add, how we deploy it, and the emails drivers will get.

8 weeksfrom kick-off to public launch
7phases, each with a GitHub milestone
29documented endpoints reused as they are
9backend changes needed before launch
9email templates, 2 restyled and 7 new

Four decisions

01

Keep Vue 3, add TypeScript

Rebuild the app in Vue 3 with Vite, TypeScript, Pinia for the session, TanStack Query for API data and Zod to check API responses.

The current app is already Vue 3, so the team keeps its tools and knowledge. Only the screens change. The API stays the same.

02

Two sites, one codebase

The marketing site is static pages built with Astro at the main domain. The signed-in app is a Vue single-page app at app. on the same domain.

The landing page needs search ranking and a fast first load on mobile data. The app needs sign-in. They share colours, fonts and components from one repo.

03

Host on Azure Static Web Apps

Both sites deploy from GitHub to Azure Static Web Apps, next to the existing API on Azure App Service.

One cloud account, free SSL, a global CDN, and a preview link for every pull request with no extra setup.

04

Backend is the critical path

The design needs a renewal order, paying from the wallet, and labelled payments. None of these exist yet. Backend work starts in week 1, alongside the frontend.

The frontend can build against mocked data, but launch is blocked until renewals work end to end.

Architecture

Two new front ends talk to the API that already exists. A daily reminder job and an SMS gateway are added. Paystack confirms payments to the API, and the API tells the open app through a live stream.

The document reader (not in the API docs)

Reads the text off a vehicle licence photo. It's a separate service from the API, and the old app calls it directly from the browser. This is the call as the old app makes it:

POST https://motorpapers-doc-parser-api.azurewebsites.net/api/vehicleDocument
Content-Type: application/json

{ "DOCUMENT_TYPE": "VEHICLE_LICENSE", "DOCUMENT": "<base64 of the image>" }

→ { "Registration Number": { "content": "KTU 604 XR" },
    "Vehicle Make":        { "content": "Toyota" },
    "Vehicle Model":       { "content": "Corolla" },
    "Vehicle Color":       { "content": "Grey" },
    "Engine Number":       { "content": "2ZR-6618023" },
    "Chassis Number":      { "content": "2T1BURHE0KC184362" },
    "Engine Capacity":     { "content": "1,798 cc" },
    "Expiry Date":         { "content": "…" },
    "Date Issued":         { "content": "…" },
    "PIN":                 { "content": "…" } }

The new app maps these labels to the API fields: Registration Number → plate_number, Vehicle Make → brand, Vehicle Model → model, Vehicle Color → color, Engine Number → engine_number, Chassis Number → chassis_number, Engine Capacity → engine_capacity, Expiry Date and PIN → the licence record. Each mapped field gets the "Read from licence" tag in the design. No sign-in token is sent, and the old app caps uploads at 4 MB.

i

Design changes the API asks for.

  • Add a Licence PIN field to Add a car. POST /vehicle-licenses requires license_pin, and the document reader already returns it as "PIN".
  • Change the upload limit in the design from 10 MB to 4 MB, which is what the old app allows. Turn PDFs into an image in the browser before sending, as the old app does with pdf.js.
  • Year isn't stored by the API. Either add year to vehicles or drop it from the cards.
  • Add a delivery address to Settings and to the renewal step. PUT /users already accepts address.
  • Add an insurer picker to the insurance step. The API lists 57 insurers.
  • Only colour is editable on a car. Show the other details as read-only, with "Contact us to change".
  • Payments can be reversed. Add a "Reversed" status pill.
  • The API also supports Facebook sign-in. The design only shows Google. Decide whether to add it.

How a payment works

Top-ups and the tracking fee both go through Paystack. The app waits for the API to hear back from Paystack before it shows a receipt, so drivers never see "paid" for a payment that failed.

!

Two implementation traps. The browser's built-in EventSource can't send an Authorization header, so open the stream with a fetch-based client such as @microsoft/fetch-event-source. Azure App Service also closes idle connections, so if no event arrives within 20 seconds, fall back to polling GET /transactions/:id every 3 seconds for up to 2 minutes. After that, show "Still confirming. We'll email you".

Backend changes

Ordered by what blocks launch. The P0 items need to be on staging by the end of week 5. Each item names the phase that needs it first.

P0

Renewal orders

POST /vehicles/:id/renewals with document_type and pay_with, plus GET /renewals. Status moves through paid, processing, out for delivery, delivered, and each change sends the renewal email. This is what the Renew button does, and it's the core of the service.

P0

Pay from the wallet

Today /transactions/initialize always sends the driver to Paystack. The tracking fee and renewals need to debit the wallet directly when the balance covers them.

P0

Say what each payment was for

Add category, description, vehicle_id and document_type to transactions, so Payments can show "Licence renewal · EKY 219 GD" instead of "credit".

P0

Longer sessions

Sign-in tokens expire after 30 minutes and there is no refresh endpoint, so drivers get signed out halfway through Add a car. Add a refresh token in an httpOnly cookie, or a sliding session.

P0

Profile and car basics

Add GET /users/me so the app can reload the profile. Document DELETE /vehicles/:id, which the old app already calls. Make POST /vehicles return 409 for a plate that's already on the account.

P0

New domains

Configuration rather than code. Allow the new app and site domains in CORS, register the new OAuth redirect URLs with Google, and set the Paystack callback URL to /payments/callback. The doc parser needs the same CORS change.

P0

Protect and document the document reader

The reader at motorpapers-doc-parser-api.azurewebsites.net isn't in the API docs and accepts requests without a token. Add it to GitBook, require the same sign-in token as the API (or rate-limit it), and return a confidence score per field so the app can flag readings to double-check.

P0

Reminder job and emails

A daily job finds papers 30, 14, 7 and 1 days from expiry and the day after expiry, then sends the matching email. Send the receipt, failed-payment, welcome and password-changed emails from the existing events. All templates are ready in emails/.

P0

Paystack webhook is the source of truth

Confirm the webhook verifies Paystack's signature, is safe to receive twice, and is what moves a transaction to success or failed. The SSE stream and emails both depend on it.

P1

Reminder settings

GET and PUT /users/notification-preferences for email, SMS and WhatsApp, the reminder days, and auto-renew. Until then, Settings hides this card behind a feature flag.

P1

SMS reminders

Connect a Nigerian SMS gateway such as Termii for the same reminder schedule as email.

P1

Recheck a pending payment

POST /transactions/:reference/verify asks Paystack again. It powers the "Check status" button on payments stuck as pending.

P1

Prices from the API

GET /pricing for the tracking fee and the renewal price of each paper, so prices aren't hard-coded in the app.

P2

Nice to have

Vehicle year, insurer on the insurance record, Facebook sign-in in the UI, and the admin user-management redesign.

How we use the repo

  • Branches: main is protected and needs passing CI plus one review. Feature branches are named after their phase, for example p2/my-cars.
  • Milestones: one per phase (P0 Foundations to P6 Launch). Every issue sits in one.
  • Labels: frontend, backend-needed, emails, design, blocked.
  • Environments: staging deploys on merge. production waits for an approver.
  • Secrets: the Static Web Apps deploy tokens for the app and the site, and the Sentry auth token. Nothing else. The repo is public, so API keys never go in it.

Settings per environment

  • VITE_API_BASE_URL: the ijanla URL for that environment
  • VITE_DOC_PARSER_URL: doc parser service
  • VITE_APP_URL and PUBLIC_SITE_URL: links between the two sites
  • VITE_SENTRY_DSN: error reporting
  • VITE_FLAG_RENEWALS, VITE_FLAG_REMINDER_SETTINGS: hide features until the API ships them

No secrets live in the front end. Paystack and Google keys stay on the API.

Switching over from the old app

  1. Launch the beta at app.<domain>. The old app keeps running.
  2. Email existing users an invite and collect feedback for a week.
  3. Redirect old routes: /home → /, /vehicles → /cars, /transactions → /payments, /login → /sign-in, /signup → /sign-up.
  4. Point the main domain at the marketing site, and send the old app address to the new app.

If something goes wrong

  • Static Web Apps keeps earlier builds. Redeploying the previous one takes minutes.
  • Keep the old App Service running for 30 days after launch as a fallback.
  • Sentry tags errors by release. Uptime checks watch the app, the site and the API.
  • Track sign-up, car added and payment success, so a drop shows up the same day.

Launch checklist

  • Domain and SSL for the site and the app, with www redirecting to the bare domain
  • CORS on the API and doc parser allows the new domains only
  • Google OAuth redirect URLs registered for production
  • Paystack live keys, callback URL and webhook URL set and tested with a real ₦100 payment
  • Email sending domain verified (SPF, DKIM, DMARC) and a reply inbox monitored
  • Reminder job scheduled, with a dry run that logs who would get an email
  • Accessibility: keyboard, screen reader and contrast pass (WCAG 2.2 AA)
  • Speed: landing page loads its main content in under 2.5 seconds on a mid-range Android phone over 4G
  • End-to-end tests green: sign up, add a car, top up, renew
  • Old-route redirects and a friendly 404 page
  • Search basics for the site: titles, descriptions, sitemap, robots, social preview image
  • Monitoring: Sentry releases, uptime checks, and analytics with a cookie notice

Risks and open questions

!

The biggest risk is renewals. If the renewal API isn't ready by week 6, launch with a "Request renewal" button that creates an order for the team to handle by hand, and switch it to the automatic flow later behind the feature flag.

  1. Which domain will the new site use? The app runs on memininode.azurewebsites.net today. The plan assumes a custom domain with an app. subdomain.
  2. Who processes renewals and deliveries today, and what does each paper cost to renew? This shapes the renewal order statuses and the prices shown in the app.
  3. What does the paid tier include? POST /vehicles takes is_paid_tier. The design assumes a ₦2,500 yearly tracking fee per car.
  4. Do reminders go out today, and from which email service? If a provider is already sending the OTP emails, the new templates can go through it.
  5. Should the document reader require sign-in? Today anyone who finds the address can send it images. Adding the same token check as the API, or at least a rate limit, protects you from abuse and surprise costs.
